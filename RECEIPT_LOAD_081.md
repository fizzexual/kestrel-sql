# Bounded receipt-map loading, isolated development 081

The candidate changes authoritative receipt-map deserialization in the standalone metadata model. It reads at most 100,000 entries into a temporary vector, sorts keys, explicitly rejects duplicates, and bulk-collects into `BTreeMap`. Unordered unique JSON keys remain accepted, sorted serialization stays identical, and the 64 MiB document limit remains. Duplicate detection can happen later than the previous insertion visitor, within the same entry/document limits and before any map is returned.

Explicit duplicate rejection is essential: Rust's [documented `BTreeMap::FromIterator` contract](https://doc.rust-lang.org/std/collections/struct.BTreeMap.html#impl-FromIterator%3C(K,+V)%3E-for-BTreeMap%3CK,+V%3E) permits duplicate values to be discarded. The installed Rust 1.97.1 implementation was inspected: it collects/sorts the input and constructs the tree in bulk. This implementation detail motivates the experiment; performance comes from the fresh 082 comparison, not a complexity claim or newer online toolchain behavior.

The original qualified 078 source is preserved. Exact derivation checks confirm that the only production change is the `batches` visitor; the only new file is its three focused tests, plus their include. All unrelated model files are byte-identical. No supported SQL-engine source or supported binary changes; Cargo.toml remains 0.3.16.
