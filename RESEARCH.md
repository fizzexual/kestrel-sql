# Research guiding KestrelSQL 0.3 and 0.3.1

Read on 6 October 2026. This is a design notebook based on primary papers and official implementation documentation. Source descriptions below are short paraphrases; implementation decisions and experiment gates are ours. Historical papers describe their publication versions, not every feature of today's engines.

The product hypothesis is an embedded metrics store that makes arbitrary time-window totals fast while keeping ingestion replayable and late data visible. We need to validate that workflow with data engineers. Individual ingredients already exist elsewhere; neither universal superiority nor algorithmic novelty follows from these readings.

The retained-handle experiment exposed a platform tradeoff: sharing one synchronous Windows handle sped boundary requests but regressed long concurrent scans. The final read path keeps the retained handle for indexed boundaries and gives long scans their own handle. It deliberately uses supported synchronous standard-library calls; opening an overlapped handle is not a drop-in substitute for Rust's synchronous file operations. See the [Rust Windows handle implementation](https://github.com/rust-lang/rust/blob/master/library/std/src/sys/pal/windows/handle.rs), whose implementation comments state that asynchronous handles are incompatible with this synchronous read path. The local regression covers 512 concurrent SQL comparisons across both paths; Linux execution is still unverified.

## The improvement sequence

The changes already implemented in 0.3 are immutable committed read views, group publication, durable batch receipts, small-segment compaction, reference-aware reclamation, retained segment handles with positional reads and a 32 MiB retained decoded-page/prefix cache. They address the coarse read/write lock, repeated boundary-page work, file opens and growing small-run counts exposed during testing. See [LIVE_METRICS.md](LIVE_METRICS.md) for the API and its limits, and [V03_RESULTS.md](V03_RESULTS.md) for actual measurements, including regressions.

For example, the implemented cache reuses decoded boundary pages and their exact local prefixes; a time-window query still performs boundary lookup and evaluates the current committed segment set. This preserves visibility of late events and avoids treating a cached whole-query answer as fresh. The corruption test warms that cache, damages a payload byte, and checks that an uncached full scrub reports damage and invalidates the cached pages. The snapshot test holds an old read view across compaction and checks that reclamation leaves its payload files accessible.

The following experiments are priorities, not delivered features:

1. **Explain the durable write tail.** Version 0.3.1 adds publication-stage timing and whole-host observations. An intermediate trial exposed slow compaction preparation; checked reads through retained input handles reduce that work in the final candidate. See [PERFORMANCE_031.md](PERFORMANCE_031.md) for the measured sequence. Storage latency and reclamation attribution remain work. Compare the current two-file publication with an append-only commit manifest while preserving identical acknowledgment semantics. Accept only after crash cut-point, corruption, disk-full and reopen tests pass.
2. **Prove a sustained service envelope.** Version 0.3.1 adds a three-round interleaved six-engine matrix. Extend this to a 30-minute mixed workload with increasing late-data fractions and batch sizes. Require no lost acknowledged batches, no unbounded segment/receipt/disk growth, and disclosed successful latency plus all failures. A single low p99 is insufficient.
3. **Accelerate generic scans.** Profile cycles and bytes per selected row before implementing selection vectors, typed batch kernels and larger sequential reads. Compare grouping, unordered predicates and broad scans; reject changes that merely accelerate one selected query while regressing others.
4. **Build the data-engineering interface.** Add a tested Arrow batch boundary, real timestamp/NULL/decimal semantics, source checkpoint records, schema versioning and useful EXPLAIN output. Benchmark connector overhead separately from the core engine. Compare extending our restricted planner with a reusable DataFusion optimizer; qualify aggregate pushdown and fallback semantics before choosing.
5. **Compare equivalent maintained state.** Benchmark against a continuously maintained prefix/rollup structure and suitable ClickHouse/Materialize configurations when a supported environment is available. Include ingestion cost, storage, freshness and late-data maintenance, not just SELECT latency.
6. **Qualify operation and recovery.** Implement backups/restores, operator-visible writer health, retention, upgrades and bounded query resources. Physical power-loss behavior and Windows directory-entry persistence need dedicated validation. Replication needs a separate distributed design and fault model.

## What would make the portfolio persuasive

A reviewer should be able to reproduce the workload, see raw samples, inspect a failing case and understand the fix. The strongest demonstration is a replayed Parquet pipeline that handles late data, matches an independent SQL oracle and survives forced process termination without duplicating acknowledged batches. Pair that with transparent performance tradeoffs and a clear architectural explanation; a claim to beat every database would undermine the evidence.
