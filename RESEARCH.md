# Research guiding KestrelSQL 0.3 and 0.3.1

Read on 6 October 2026. This is a design notebook based on primary papers and official implementation documentation. Source descriptions below are short paraphrases; implementation decisions and experiment gates are ours. Historical papers describe their publication versions, not every feature of today's engines.

The product hypothesis is an embedded metrics store that makes arbitrary time-window totals fast while keeping ingestion replayable and late data visible. We need to validate that workflow with data engineers. Individual ingredients already exist elsewhere; neither universal superiority nor algorithmic novelty follows from these readings.

The retained-handle experiment exposed a platform tradeoff: sharing one synchronous Windows handle sped boundary requests but regressed long concurrent scans. The final read path keeps the retained handle for indexed boundaries and gives long scans their own handle. It deliberately uses supported synchronous standard-library calls; opening an overlapped handle is not a drop-in substitute for Rust's synchronous file operations. See the [Rust Windows handle implementation](https://github.com/rust-lang/rust/blob/master/library/std/src/sys/pal/windows/handle.rs), whose implementation comments state that asynchronous handles are incompatible with this synchronous read path. The local regression covers 512 concurrent SQL comparisons across both paths; Linux execution is still unverified.

## The improvement sequence

The 0.3.7 source wrapper addresses Kafka's documented external-sink coordination boundary by encoding a canonical source identity/start/next into the existing durable receipt. This keeps output and the local resume position in one publication, preserving CAT4/SEG2 and avoiding a second checkpoint sync. A borrowed prefix iterator validates/reconstructs source progress without copying unrelated IDs. [PERFORMANCE_037.md](PERFORMANCE_037.md) retains identical catalog byte costs against matched manual IDs, variable write tails and source-specific fault/replay/Parquet evidence. This is archive-local checkpoint atomicity. Empty-output advances, source reset, bounded receipt retention, consumer lease epochs and distributed fencing still require explicit designs and tests.

The 0.3.6 experiment profiles payload fingerprinting separately from request transport. Chunked SHA-256 updates offer only a small gain for the usual batch and regress tiny batches, so that trial remains unpromoted. The implemented `PreparedBatch` owns immutable input, hashes it inside the library once, and lets confirmed embedded retries reuse that identity. [Arrow's in-memory model](https://arrow.apache.org/docs/python/data.html) supplies context for immutable column batches and shallow reuse; Kestrel has no Arrow adapter. [sha2 0.10.9](https://docs.rs/crate/sha2/0.10.9) documents the existing hash dependency. [PERFORMANCE_036.md](PERFORMANCE_036.md) discloses amortized preparation, preparation on every call, ordinary controls and caller-owned buffer memory. Unknown IDs still use synchronized publication, and a prepared value never substitutes for a durable receipt or source checkpoint.

The 0.3.5 experiment follows a measured local bottleneck: a known committed retry still queued behind new publication, compaction and optional collection waiting. `LiveArchive::with_retry_index` validates confirmed receipts through a second bounded lookup, extending it only after durable publication and publication of the read view. It stays off by default after a write-heavy trial regression; the final default and enabled paths are compared on the same binary. Unknown or pending IDs retain writer validation; observed poisoning or exit rejects every append until reopening. This is a deliberate additional-memory/startup tradeoff, not a new deduplication algorithm or end-to-end exactly-once guarantee. [PERFORMANCE_035.md](PERFORMANCE_035.md) compares pure retries, retries mixed with fresh writes, overload, ordinary write controls, a fresh DuckDB reference and the embedded Rust API. A feature-only stalled-writer test checks availability without a latency threshold; injected publication failures check health and recovery.

The 0.3.4 experiment revisits coalescing using fresh, same-binary policy comparisons. The retained 0.3.3 50K-ID profiles spend most measured publication time in segment/catalog synchronization, while preparation is small. [PostgreSQL 18 WAL settings](https://www.postgresql.org/docs/18/runtime-config-wal.html) describe the throughput/latency tradeoff of commit delays and why low-concurrency waits can be wasted. Kestrel tests explicit 0/2/8 ms windows, retains the zero-delay default, and limits optional waits to a non-sliding 20 ms deadline. Its immutable two-file publication is different from PostgreSQL WAL group flushes. See [PERFORMANCE_034.md](PERFORMANCE_034.md) for independent confirmation and regressions; adding a timer is not evidence that storage stalls are fixed.

Version 0.3.3 tests immutable receipt deltas with full checkpoints, informed by [RocksDB MANIFEST](https://github.com/facebook/rocksdb/wiki/MANIFEST) snapshot/edit records. [SQLite WAL](https://www.sqlite.org/wal.html) separately describes checkpoints and synchronization costs. This candidate is a chain of complete, immutable catalog files; it is not an append-in-place WAL. It retains segment and catalog synchronization before acknowledgment. Every current receipt dependency is preserved during reclamation, and recovery validates at most 32 files. Missing dependencies and invalid receipt histories fail closed. A separately feature-enabled driver tests exact publication cuts and injected disk-full OS errors; default binaries reopen and replay. These tests do not simulate actual device exhaustion or physical power loss. [PERFORMANCE_033.md](PERFORMANCE_033.md) retains the byte reduction, repeated latency comparisons and failed service cases.

Version 0.3.2 applies reusable row selections and typed ungrouped reductions, informed by the vector-processing readings above, and reuses page buffers. This is a portable scalar implementation; no explicit SIMD claim is made. Opt-in scan timings and uninstrumented alternating comparisons are in [PERFORMANCE_032.md](PERFORMANCE_032.md). The service tests expose long synchronization/publication stalls even when CPU work is small, so query speed and the durable service envelope require separate evidence.

The changes already implemented in 0.3 are immutable committed read views, group publication, durable batch receipts, small-segment compaction, reference-aware reclamation, retained segment handles with positional reads and a 32 MiB retained decoded-page/prefix cache. They address the coarse read/write lock, repeated boundary-page work, file opens and growing small-run counts exposed during testing. See [LIVE_METRICS.md](LIVE_METRICS.md) for the API and its limits, and [V03_RESULTS.md](V03_RESULTS.md) for actual measurements, including regressions.

For example, the implemented cache reuses decoded boundary pages and their exact local prefixes; a time-window query still performs boundary lookup and evaluates the current committed segment set. This preserves visibility of late events and avoids treating a cached whole-query answer as fresh. The corruption test warms that cache, damages a payload byte, and checks that an uncached full scrub reports damage and invalidates the cached pages. The snapshot test holds an old read view across compaction and checks that reclamation leaves its payload files accessible.

The following experiments are priorities, not delivered features:

1. **Explain the durable write tail.** Version 0.3.1 adds publication-stage timing and whole-host observations. An intermediate trial exposed slow compaction preparation; checked reads through retained input handles reduce that work in the final candidate. See [PERFORMANCE_031.md](PERFORMANCE_031.md) for the measured sequence. Storage latency and reclamation attribution remain work. Compare the current two-file publication with an append-only commit manifest while preserving identical acknowledgment semantics. Accept only after crash cut-point, corruption, disk-full and reopen tests pass.
2. **Prove a sustained service envelope.** Version 0.3.1 adds a three-round interleaved six-engine matrix. Extend this to a 30-minute mixed workload with increasing late-data fractions and batch sizes. Require no lost acknowledged batches, no unbounded segment/receipt/disk growth, and disclosed successful latency plus all failures. A single low p99 is insufficient.
3. **Accelerate generic scans.** Profile cycles and bytes per selected row before implementing selection vectors, typed batch kernels and larger sequential reads. Compare grouping, unordered predicates and broad scans; reject changes that merely accelerate one selected query while regressing others.
4. **Build the data-engineering interface.** Add a tested Arrow batch boundary, real timestamp/NULL/decimal semantics, source checkpoint records, schema versioning and useful EXPLAIN output. Benchmark connector overhead separately from the core engine. Compare extending our restricted planner with a reusable DataFusion optimizer; qualify aggregate pushdown and fallback semantics before choosing.
5. **Compare equivalent maintained state.** Benchmark against a continuously maintained prefix/rollup structure and suitable ClickHouse/Materialize configurations when a supported environment is available. Include ingestion cost, storage, freshness and late-data maintenance, not just SELECT latency.
6. **Qualify operation and recovery.** Implement backups/restores, operator-visible writer health, retention, upgrades and bounded query resources. Physical power-loss behavior and Windows directory-entry persistence need dedicated validation. Replication needs a separate distributed design and fault model.

## What would make the portfolio persuasive

A reviewer should be able to reproduce the workload, see raw samples, inspect a failing case and understand the fix. The strongest demonstration is a replayed Parquet pipeline that handles late data, matches an independent SQL oracle and survives forced process termination without duplicating acknowledged batches. Pair that with transparent performance tradeoffs and a clear architectural explanation; a claim to beat every database would undermine the evidence.

## Adaptive integer grouping in 0.3.8

The measured group loop spent time hashing each selected key, looking up a vector of general aggregate cells and dispatching every expression for every row. The candidate uses a bounded direct-address table for compact integer spans, narrow arrays and shared SUM/AVG reductions. Independent CRC-checked scans still read the current snapshot; no whole-query answer is cached. Wide keys retain hash fallback. Signed edges, filtered holes, snapshot/reopen and memory/result budgets are tested.

This technique has established prior art. DuckDB documents choosing an array indexed by the group key when column statistics show a sufficiently small domain; its perfect-hash threshold controls that choice. See [DuckDB's dimension-table article](https://www.duckdb.org/2026/10/02/dimension-tables) and [aggregation design](https://www.duckdb.org/2022/03/07/aggregate-hashtable). Our value is implementing and qualifying an adaptive path alongside the existing embedded range indexes and source-checkpoint workflow, rather than claiming a new aggregation algorithm. [Current evidence](PERFORMANCE_038.md) retains both competitive wins and losses, misleading fixture evidence and control drift.

## 0.3.9 tagged lookup experiment

The measured sparse reduction path keeps [Rust's standard randomized HashMap](https://doc.rust-lang.org/std/collections/struct.HashMap.html) as the authoritative key map, while reusing exact key/slot hits in a small query-local cache. Collision and high-cardinality overhead in the first cached candidate motivated a block-specialized plain hash path and a minimum-hit heuristic. These are established optimization techniques, with no novelty claim. [All current measurements and rejected intermediate evidence](PERFORMANCE_039.md) remain reproducible.

## 0.3.10 first-filter selection

Stage instrumentation located the added unordered-scan cost in selection. An `inline(never)` trial produced no reliable end-to-end gain. [Rust's reference describes inline annotations as hints](https://doc.rust-lang.org/reference/attributes/codegen.html#the-inline-attribute), so an annotation is a hypothesis to measure, not a speed guarantee. Building row positions directly from the first residual predicate removes an initial range fill and indirect value lookups. Operator fusion is established prior art; no novelty claim is made. [Final controls, complete matrix and retained unsuccessful evidence](PERFORMANCE_040.md) support the measured scope.

## 0.3.11 seeded sparse-cache indexing

Low-bit-aligned keys defeated the xor-fold index. A full-width multiply spreads those keys, but fixed multipliers have their own adversarial spacings. The candidate derives an odd multiplier once per query using [Rust RandomState](https://doc.rust-lang.org/std/collections/hash_map/struct.RandomState.html) and [BuildHasher::hash_one](https://doc.rust-lang.org/std/hash/trait.BuildHasher.html#method.hash_one). Exact tags and the authoritative randomized HashMap retain correctness. Tests invert each actual multiplier to force real collisions; the matrix adds Fibonacci/power-of-two patterns. This is established cache/indexing work, without cryptographic or novelty claims. [Current measurements and remaining losses](PERFORMANCE_041.md).

## 0.3.12 reuse-triggered cache

Measured reuse can justify a wider lookup table after small-cache fallback. The first trial paid the allocation cost on tiny queries after their final block; delaying allocation until the next nonempty block avoids unused work. Exact tags, an authoritative randomized map, a key budget, a hit-rate gate and one promotion attempt preserve correctness and bound additional memory. Seed-specific collision, irregular signed-key, growing-cardinality and beyond-i64 reduction checks accompany the final timings. This is established adaptive caching, without a novelty claim. [Evidence and every tradeoff](PERFORMANCE_042.md).

## 0.3.13 dense reduction fusion

A selected-row slot pass followed by another reduction pass imposed measurable aggregation cost on dense GROUP SUM. Combining exact counts and a shared SUM/AVG column removes that second traversal while preserving metadata bounds and signed wide reductions. Final binaries are independently rebuilt and compared at 10M and 100M rows; mixed and sparse paths retain their preceding implementation. This is established loop fusion and specialization, without a novelty claim. [Evidence and tradeoffs](PERFORMANCE_043.md).

## 0.3.14 sparse kernel selection

A fused loop can help small sparse states yet regress wider key sets. Exact cache hits need no tag rewrite; a typed shared SUM can be reduced during small-cache lookup, while wider kernels retain a separately measured two-pass mapper. Four preserved trials and alternating guards support this bounded choice. Source identity proves unchanged dense/scan/read/write paths; changes in their measured timings are retained without attribution. This is established specialization, without a novelty claim. [Evidence and unsuccessful trials](PERFORMANCE_044.md).

## 0.3.15 bounded reader reuse

Repeated file opens matter when queries visit many small segments. An offset-only read trial did not convincingly improve the target scan, so its source and results remain unselected. A separately measured cache transfers exclusive file ownership between query-local readers, retaining at most one idle file per segment and 128 per archive. Payload checksum reads and fresh scrubs remain required; compaction, pinned snapshots and handle lifetime receive direct tests. Resource tradeoffs and every slower control are explicit. Source identity proves unchanged group kernels, serialized formats and durable publication policy. This is established resource reuse without a novelty claim. [Evidence and both trials](PERFORMANCE_045.md).

## 0.3.16 packed medium cache

An exact key plus checked slot-plus-one needs less space than an Option tuple on the local 64-bit layout. Zero marks an empty slot independently of the signed key, and the authoritative randomized HashMap still handles collisions. Predeclared paired criteria, explicit memory tests, an independent zero/signed/collision oracle and full qualification support this change. Both initial build failures and every slower guard remain visible. This is established representation tuning without a novelty claim. [Evidence and limits](PERFORMANCE_046.md).
