# Inspect or reproduce encoder profiles 065 and 066

The ZIP preserves separate `065` and `066` folders under `kestrel-sql/benchmarks/encoder-profiles-065-066/`. They contain original policies, raw JSON/stdout/stderr/status, exact input JSON and envelopes, source, diagnostics and the identical frozen probe. Verify the ZIP checksum and `ENCODER_PROFILES_065_066_MANIFEST.sha256` first. No database is needed for inspection.

The canonical workspace has `work/perf-065` and `work/perf-066`, with released source at `outputs/kestrel-sql`. Scripts infer this work/outputs topology. Repository evidence copies omit the large input copies, which remain inside the full ZIP. Do not run scripts directly under the repository's benchmarks folder, overwrite original evidence or silently rerun completed cases.

065 extracts typed borrowed serializer definitions from released `src/archive.rs`. `prepare.py` copies three full checkpoint bodies/envelopes from the hash-verified 064 baseline-A fixtures, preserves committed-then-added ordering through the original final receipt ID, and freezes four-round case order before compilation. `build.py` links one standalone probe to the exact serde/serde_json release libraries already built in 064. Its commands and library/source/executable hashes are in `build.json`. For a fresh reproduction where those caches are unavailable, rebuild the same released dependencies with the recorded Cargo.lock/compiler first. No engine source is modified.

`smoke.py` runs 48 synthetic byte/JSON checks, nine two-encode real-input diagnostics and three capacity traces. They are excluded from all competitive samples. Capacity changes are not allocator calls. The original output bytes, envelope CRCs and SHA-256 values are independent of the models.

In a fresh result directory, run `check_processes.ps1 pre-timing`, `run.py --initialize`, then `run.py`. The script freezes binary/source/harness/policy/inputs and runs one probe at a time. Every case includes 33 encodes with no warmup, the first allocation charged, and exact output comparison outside timers. Baseline A/B share the same executable and mode. Exact reservation knows future output length solely for this fixed-input model. Reuse retains capacity within one case.

After timers finish, run `check_processes.ps1 post-timing` and `audit.py`. It verifies byte/input/source provenance, raw hashes, Latin-square order, process/build timing, Type 7 quantiles, all paired ratios and memory guards. 065 has one failed first-encode calibration ratio 1.100009428487 beyond 1.10; its advance decisions remain false.

066 is a separate 144-case/twelve-round replication prepared after that failure. It reuses the same executable, inputs and original smoke evidence, with no rebuild, diagnostic rerun or original case replacement. Thresholds remain the same. `replication-provenance.json` freezes its adapted twelve-round auditor before timing. The policy's aggregation sentence retains “four” accidentally; `aggregation-text-note.json` records this documentation error before final ratio analysis, leaves the policy/source unchanged, and points to the twelve-round code/case list. The actual aggregation is the median of all twelve within-round ratios. All 43 replication checks pass; none of this promotes an engine.

The full ZIP includes both copies of all six input files, every raw sample/status/error, original failed 065 audit and successful 066 audit, source and probe binaries, capacity diagnostics and bounded cache-reclamation proof. No stores or inputs are deleted. After both timers ended, only two tagged 064 debug caches were reclaimed; all measured frozen binaries and their verified private archive remain intact.

These profiles measure CPU serialization/allocation for fixed borrowed catalogs, rather than append latency, sync, source replay, SQL, network throughput or durability. A future engine candidate must undergo its own full recovery, memory and native/service qualification. The released 0.3.16 tree and issued morning report remain frozen.
