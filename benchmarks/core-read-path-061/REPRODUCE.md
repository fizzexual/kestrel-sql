Download the private supplemental ZIP linked from `CORE_READ_PATH_061.md`, verify its SHA-256 sidecar, extract it, and verify `CORE_READ_PATH_061_MANIFEST.sha256` within `kestrel-sql`. The ZIP contains all fresh service/recovery stores and every timed analytical input, including the full 100M-row Kestrel archive and DuckDB reference. The original environment used Rust 1.97.1, the repository MSRV is 1.89, and the host had 20 logical processors. Set `PYTHONPATH` to the dependency directories. Each replay prepends its own copied benchmark helpers to that path. Leave enough free disk for its copied input and fresh stores; service preflight requires more than 800MB before each case. The original timed inputs occupy multiple GB. Do not run compilation, another database workload, an audit, packaging, cache cleanup or Git operations during timing.

From the extracted `benchmarks/core-read-path-061` evidence directory, run one of these sequentially. Each destination must not already exist. Input hashes are verified and exact input copies are made before the selected phase begins; original policies and samples are retained separately.

The range phase performs 21 alternating process pairs, four 100/1,000-row shapes, 101 native query samples per shape and three warmups. It checks exact returned rows and CRCs after the timers. The analytical phase rotates baseline/candidate/DuckDB order across three rounds for each of 12 preserved fixtures, five queries per fixture, 11 timed samples per shape and three warmups. DuckDB uses one thread and a 256MB buffer limit. Each native process validates the executable version and row count, then performs a full scrub and stops. DuckDB connections close after each case.

The service phase uses fresh 1M-row stores, 64 clients, a bounded 256-request queue, two-second worker expiry, zero intentional group delay and 100-row append batches. It runs all 36 predeclared cases, including one-minute soaks and overload, and retains every request sample, error, expired request and dropped arrival. It checks cold reopen, atomicity, acknowledged batch presence, exact retry, 20 NumPy windows per store and every data CRC outside each arrival timer. It stops each task-owned bridge after its case. The `write` profile contains 25% writes; mixed contains 5%, scan 10%, read 0%. Offered schedules are not sustainable-capacity measurements.
