# Receipt-page hypothesis 072 — separate storage model

Status: development model, before engine integration or timed performance qualification. Supported KestrelSQL 0.3.16 is unchanged. This format is never written into a real Kestrel archive.

Released CAT4 checkpoints serialize all committed receipts whenever the bounded 32-catalog delta chain resets. Diagnostic 068 identified large checkpoint write/sync stalls. Compression models 069–071 did not qualify a replacement. This model instead preserves sealed, immutable pages of 512 complete receipts. A commit rewrites only the unfinished tail and any newly filled pages, then publishes a new root referencing every page. No receipt is evicted. Actual new IDs, payload digests, row counts and original generations are preserved; an exact retry performs no publication. A metadata-only publication reuses every page.

Files have distinct model-only magic: KPAG0721 (page) and KROT0721 (root). Both use a 16-byte envelope containing magic, length and CRC32. Root references carry page generation, ordinal slot, count and payload CRC. Names are derived from numeric fields, never supplied paths. Bounds: 100,000 receipts, 512 entries/page, 196 page references, 256 KiB/page, 512 KiB/root, 64 MiB legacy checkpoint, 64 schema columns, 10,000 segment references, 4,096 source keys. Length limits are checked before file allocation; receipt/page/reference collections have bounded deserializers. Every sealed page is full, the final page is nonempty, ordinals are consecutive, counts agree, generations are valid, and duplicate IDs/unknown fields/trailing bytes are rejected. CRC is accidental-corruption detection, not authentication.

Publication creates immutable page files, writes/flushes/syncs each changed page, writes/flushes/syncs a pending root, closes and renames it to a final generation name. Unix also syncs the directory. Any publication error poisons the writer; reopening chooses the highest final root and validates all dependencies. A malformed highest root fails closed rather than falling back. Orphan page/pending-root generations advance the next generation after reopening, preventing name reuse. A kill before root publication leaves the old receipt history; a kill after publication exposes the complete new history. Windows process-kill tests do not establish physical power-loss safety or durable rename guarantees.

The legacy importer accepts only a complete CAT4 checkpoint (receipt_base null), validates its envelope/schema/receipts and writes a separate model directory. It cannot migrate a CAT4 delta chain or older CAT2/CAT3 stores. It does not replace or edit the original file. A future engine format would need explicit versioning, complete old-format migration, existing segment validation and SQL/source/live-service/recovery tests. The old engine must reject the new magic; increasing its existing 32-chain budget is not part of this hypothesis.

Source positions are rebuilt from all canonical ksrc1 receipts using the released source-key domain and contiguous interval/increasing-generation rules. This verifies metadata reconstruction and durable retry identity, not transactional delivery from an external source. The harness enforces one process per model store; the prototype does not implement the engine's exclusive file lock or concurrent writers. Segment references remain opaque model metadata: the model does not write/query/verify data segments. No SQL, compaction, snapshot pinning, reclamation or service throughput is qualified here. No model file is deleted, including orphan, interrupted or failed cases. Reclamation and real pinned-reader safety require a later engine implementation.

Qualification comes before timing: debug/release tests, strict lint, three unchanged real generation-129 checkpoints (126/50,126/99,126 receipts), actual changing receipts/source intervals, a separate Python full-file oracle, injected-error cuts and controlled process kills, and checks that old receipts remain exact after every reopen. A later benchmark must use independently balanced A/B/C positions, charge tail/root encoding and every changed-file write/sync/rename, report one-time migration/recovery/storage amplification, retain controls/stalls/failures, and compare the same logical edits. Reusing identical snapshots alone would not test this hypothesis.
